# X-Agent · 智能体池匹配网络

> 你的 agent 已经很懂你了 — X 把这份「懂」，变成一次相遇。

每个人身边都有越来越懂自己的 agent（Muse、ChatGPT、Gemini、各类助手）。
X-Agent 不再让用户填一遍表：它接入这些 agent 的记忆，**蒸馏**成一张可计算的
结构化画像，再在池子里做**双边匹配** — 婚恋、交友、求职、创业伙伴，同一套引擎。

**核心卖点**

1. **蒸馏，而非搬运**：原始聊天永不离开用户侧；进入池子的只有蒸馏后的结构化画像。隐私靠蒸馏解决。
2. **双边匹配**：最终分 = 两个方向分数的调和平均。她合你、你也得合她 — 单相思，沉底。
3. **可解释**：每个分数都带理由（谁覆盖了谁的哪些需求、共同看重什么、哪条特质互补）。黑盒匹配讲不出故事，我们讲得出。
4. **场景可插拔**：场景 = 一份声明式配置（schema 词表 + 打分轴 + 权重）。换场景只改配置，引擎不动。
5. **活画像**：聊天与反馈持续蒸馏、并入画像；反馈会变成显式的门槛偏好，而不是偷偷重掷骰子。

## 架构

```
 用户的 agents                X-Agent                      匹配池
 ┌────────────┐   原始材料   ┌──────────────────┐
 │ 日常助手    │ ───────────▶ │ 蒸馏算子 D         │   画像卡（结构化）
 │ 工作 agent  │  (不出用户侧) │  prompt 由场景配置  │ ───────────────▶ 池中流转
 │ 情感咨询    │              │  自动生成           │
 └────────────┘              └──────────────────┘
        ▲                             │  merge（置信度加权）
        └──── 追问 / 反馈 ────────────┘

 匹配：硬约束过滤 → 双向 needs/offers 交叉覆盖 + 价值观 + 特质(sim/comp) + 兴趣
       → 调和平均 → 带理由的排名    （池级全局配对 = 双边稳定匹配问题，可扩展）
```

**算子分解**：`画像_场景 = Project_场景( Distill_通用(原始材料) )`
通用蒸馏回答"这个人是谁"；场景投影回答"在这个场景里，该看他的什么"。
同一句"我经常熬夜赶项目"：婚恋投影读出*作息不规律*，创业投影读出*执行力强*。

## 目录

```
core/schema.py       画像结构定义 + 校验/归一化
core/distill.py      蒸馏算子 D（LLM 抽取，prompt 由场景配置生成）+ merge 算子
core/match.py        匹配引擎：硬过滤、双向打分、理由生成、反馈重排（纯函数，零依赖）
scenarios/dating.json  婚恋场景配置：词表、特质轴(sim/comp)、权重、硬规则
data/personas.json   13 个 persona 的预蒸馏画像（主角阿哲 + 12 位候选人）
data/raw_logs/       阿哲的原始材料示例（三个源 agent 的记忆拼接）
scripts/distill_persona.py  CLI：原始材料 → 画像卡
scripts/build_demo_data.py  跑真实引擎，生成 demo 数据
demo/index.html      单文件演示前端（零依赖 canvas 星云 + 红线）
```

## 快速开始

```bash
# 1. 生成演示数据（跑的是真实匹配引擎，不是写死的假数据）
python3 scripts/build_demo_data.py

# 2. 起服务看 demo
cd demo && python3 -m http.server 8000
# 打开 http://localhost:8000 → 点「自动演示」
```

核心引擎零第三方依赖（Python 3 标准库）。蒸馏才需要 LLM：

```bash
export LLM_BASE_URL=https://sem.ensureok.ai/v1   # 任意 OpenAI 兼容端点
export LLM_API_KEY=<你的 key>
export LLM_MODEL=<端点模型列表里的模型名>
python3 scripts/distill_persona.py \
  --raw data/raw_logs/azhe.md \
  --scenario scenarios/dating.json \
  --out /tmp/azhe.json
```

## Demo 讲稿（2–3 分钟）

| 时间 | 动作 | 要讲的一句 |
|---|---|---|
| 0:00 | 点「接入我的 Agents」 | 三个 agent 的记忆汇成一张画像卡 — 原始文本不出用户侧 |
| 0:40 | 点「和我聊聊」 | 画像是活的：追问 → 再蒸馏 → 置信度加权 merge |
| 1:20 | 点「开始匹配」 | 先硬约束、再双向分；异地/吸烟当场淘汰且给理由 |
| 2:00 | 红线锁定林小满 | 打开理由面板：双向需求覆盖 + 调和平均，单相思沉底（苏晴第 3 就是证据） |
| 2:30 | 点「反馈：太安静了」 | 反馈变成显式门槛，林小满降权、陈语桐胜出 — 不是重掷骰子 |

预置的叙事机关（都在真实引擎里跑出来，不是演的）：
- **林小满**（0.935）：needs/offers 双向全覆盖 → 冠军
- **苏晴**（0.495）：纸面与阿哲几乎同类，但给不了他要的 → 被调和平均压到第 3
- **沈亦舟**：条件近乎满分，但在北京 → 硬约束淘汰（分数 0，理由写明）
- **陆蔓**：吸烟触发 dealbreaker → 淘汰

## 加一个新场景（求职 / 创业伙伴）

复制 `scenarios/dating.json`，改四样东西即可，引擎与前端不动：

1. `values_vocab` / `needs_offers_vocab`：该场景的受控词表（求职的 offers = 技能，求职的 needs = 岗位诉求）
2. `trait_axes`：每条轴标注 `sim`（求同）还是 `comp`（互补）与权重（创业伙伴：技能互补、风险偏好求同）
3. `weights`：四个分项的权重
4. 硬规则目前写在 `core/match.py: hard_filter` — 新场景的硬规则在那里按 scenario 名分支添加

## 路线图（队友接手从这里开始）

- [ ] 场景二选一落地：`scenarios/cofounder.json` 或 `scenarios/jobs.json`，并造第二组 personas 验证"同引擎、换配置"
- [ ] 蒸馏接入真实 agent：把源 agent 换成 MCP server，暴露 `get_user_model` 工具（架构故事已按此设计）
- [ ] 池级配对：从 top-1 扩展到全局稳定匹配（Gale–Shapley），演示"全场配对完成"的收尾动画
- [ ] 画像更新闭环：聊天 UI 输入真实回答 → 调蒸馏 → merge → 重排（demo 里目前是脚本化的 QA beats）
- [ ] 前端：候选人节点点击查看对方画像卡（双向视角切换：看"我合她多少"）
- [ ] 权重学习：多次反馈后用简单在线学习调 `weights`，而不是只做门槛

## 设计原则（改代码前先看）

- 匹配函数必须是**纯函数 + 确定性输出**：同样的输入永远同样的排名，demo 现场不许有随机性。
- 任何分数都要能生成**人类可读的理由**；给不出理由的分项不要加。
- 原始文本只出现在 `data/raw_logs/` 这类用户侧材料里，**永不进入 personas / 池数据结构**。
