# 四进程 Agent 通信与用户补问设计

本阶段把已有单进程确定性原型推进为四个独立本地 Agent。每个程序占用自己的 HTTP 端口，以简单 TUI 提供自己的终端窗口、公开画像和用户对话。窗口数量用于展示，协议始终是两两会话。主场景为寻找创业合伙人；场地案例只验证同一内核的最小路径。

本规格供实施前评审；尚未表示代码已实现。用户已明确采用本地多进程、独立端口及 1:1 通信。模型供应商、模型名和自定义地址等待用户提供，凭据只在本地配置。缺少模型配置时可运行明确标识的确定性模式，不能将其报告为真实模型验收。

## 运行方式

建议端口为 8011、8012、8013、8014，以免与已有 8000 原型冲突。四个进程运行同一份程序，各加载自己的配置、用户身份、画像、数据库和模型上下文。每个进程同时运行本方 TUI 与异步 HTTP 服务，在四个终端窗口或分屏中分别启动；HTTP 收发不能被键盘输入阻塞。提供无 TUI 的 headless 启动方式用于自动化多进程测试。开发脚本不做业务路由，不强依赖 tmux 或特定终端软件。

没有中央工作台、广播服务或共享会话数据库。Agent 1 的发送操作将同一条公开需求分别经 HTTP 投递到已配置的三个对端；Agent 1 自己保存该次需求的候选状态。TUI 只是读取所属运行时的事件和提交所属用户的操作；跨 Agent 的通信必须经过真实 HTTP，不能直接访问对端内存或数据库。

每个 TUI 顶部显示 Agent 名称、端口、公开 profile 标签和运行模式；中部显示可滚动的消息记录与会话状态；底部保留用户输入框。区分用户消息、对端 Agent 消息、本方公开动作摘要和系统状态；不展示模型内部推理。多个会话通过短编号或会话选择器切换，补问明确显示归属会话，不能把回答发送给错误对端。程序重启从本方存储恢复待答问题。

回车发送需求或回答，批准与拒绝使用明确的 TUI 按钮或命令，普通回答不能被解释为批准。结果以终端面板显示并可导出 JSON。本阶段不新增网页或原生桌面程序，不做额外总览界面。原有 web 原型保留作为上一阶段产物。

## 三种方案的取舍

推荐四个相同运行时的独立 HTTP 进程：窗口与实际进程一一对应、没有中央业务服务、能够验证进程重启和对端离线。单进程模拟四个角色不能证明本阶段目标。四个进程加中央编排器会增加路由与状态归属，本阶段不采用。

## 通用内核与场景边界

通用对象包括 AgentIdentity、PublicProfile、Demand、Requirement、PairSession、PeerMessage、OwnerQuestion、Decision、Proposal、Approval 和 Result。参与者、问题选项、字段名、标签和结果内容从配置或结构化决策读取；不得按 agent-2、agent-3 或 cofounder 分支决定业务结果。

运行时负责消息投递、会话状态、暂停恢复、重试、身份校验、版本、预算和确认门控。场景定义字段类型、允许的条件操作符、可交流字段和结果格式。Policy 决定下一步动作；Transport 负责通信；Memory 接口负责本方已确认信息。现有 SQLite 事务与幂等机制可复用，但存储类不再写入场景专属台词和决策。

本阶段完成明确标识的 X-Agent HTTP JSON 消息协议和 Transport 接口，不将自定义 HTTP 接口宣称为标准 A2A。标准 A2A 绑定留作后续适配，可复用已调研 SDK；模型决策、场景配置不依赖具体传输格式。四进程真实 HTTP 是本阶段必须项。

## 粗筛与双边会话

用户 1 在对话框输入需求，回车触发结构化提取、校验和发送；界面显示实际公开的条件。若关键条件有歧义，先询问用户，禁止模型凭空补齐未表达的硬条件。用户可校正已提取条件，校正生成新的需求版本并通知受影响会话；发送内容仅来自用户明确表达的需求与允许公开的画像字段。

每个接收进程先打印 REQUEST_RECEIVED，再根据公开需求与本方公开画像执行确定性粗筛，返回 PASS、FAIL 或 UNKNOWN 及字段级原因。明确 FAIL 时记录 FILTERED 并停止后续模型交流；UNKNOWN 是待澄清信息，不能被解释成满足或直接淘汰。

Agent 1 与通过或待澄清的候选各自建立一个 PairSession。三个会话互不阻塞：2 被过滤不影响 3、4；3 等待用户也不阻塞 4。需求有 request_id，双边会话有 session_id；它们不能混用。更改投入时间等事实必须能改变筛选结果。

演示夹具可以安排 2 明确不满足初始硬条件，3 与 4 满足；后续回答让 4 与新条件冲突、3 达成一致。但程序不能固定挑选 3。互换 3 与 4 的条件时，结果必须随之变化。

## 消息与状态归属

消息至少包含 schema_version、message_id、request_id、session_id、sender_agent_id、recipient_agent_id、type、causation_id 和 payload。发送者身份由服务端对端凭据验证，不能只相信 JSON 中的 sender。接收端从配置解析可信对端地址，模型不能指定任意 URL。

消息类型覆盖需求、筛选结果、询问事实、提供事实、提案、接受、拒绝和用户批准。所有私有字段先投影为允许发送的字段；公开摘要优先由通过校验的数据生成。

双方共享会话标识和提案摘要，各自维护本地 revision；不把本地 revision 当作跨进程全局版本。用户操作携带所属进程的 expected_revision。提案拥有独立版本，接受和批准必须绑定同一规范化摘要。

HTTP 收到消息后先原子写入 inbox 并返回接收结果，再交由本地工作任务处理，避免递归同步 HTTP 调用导致互等。每个双边会话串行处理，候选之间并行。对外消息先进入 outbox，按 message_id 重试；接收端去重，避免重复触发模型和事件。进程重启后重扫未处理 inbox 与未送达 outbox。

本阶段采用固定同机对端配置与合成身份凭据，监听 127.0.0.1；不声称生产身份认证。HTTP 确认接收与业务接受是两个不同事件。

## Agent 决策与向用户补问

统一 Decision 结构包含 action、public_summary、facts 或 terms、question 和 evidence_refs。action 只允许 ASK_PEER、ASK_OWNER、PROPOSE、ACCEPT、REJECT、WAIT 等声明的动作。OWNER_APPROVAL 不属于模型动作。

只有本方画像、经授权的记忆、当前需求和对端已公开信息进入本方模型上下文。输出须经严格结构校验；规则层检查字段权限、硬条件和状态是否合法。格式错误最多修复一次，仍失败进入可重试错误，不伪装成功或无限循环。真实模式记录 provider、model、耗时、调用次数及可得的 token 用量，不记录密钥。

Agent 可因未知事实、偏好不明确或权限不足提出 OwnerQuestion。问题包含 question_id、归属用户、原因、字段、回答形式、保存范围和受影响会话。进入 WAITING_INPUT 后持久化并向 TUI 发布事件；终端退出后重启不丢失问题。用户回答通过校验后恢复原会话并重新决策，不由 TUI 直接选择后续状态。

用户 1 的额外要求可以属于整个 request，也可以只属于一个 PairSession。相同 request 下对同一缺失字段的追问合并为一张问题卡；回答仅发送给明确受影响、仍在进行的候选会话。双方用户都可能被问，窗口 3 或 4 的回答必须提交到各自进程。

已确认的稳定事实或偏好可以保存到本方 Memory 接口；本次特例保存在会话覆盖层。持久化与对外披露分开；长期保存不意味着自动广播。完整记忆管理界面和向量检索不纳入本阶段，最小存取接口需为后续跨会话复用保留。

初始上限建议为每个双边会话 6 次模型决策、2 次用户补问；每次调用 20 秒超时。预算由配置控制，实际值在实现计划中结合模型能力固定。用户等待不占用 HTTP 请求或模型调用，拒绝和终态不能继续自动发送。

## 提案与批准

双方 Agent 就同一结构化提案达成一致后进入 PENDING_APPROVAL。各用户在自己窗口批准，批准以独立消息发送给对方。模型的 ACCEPT 不等于用户批准。

提案摘要绑定 scenario_id、双方身份、规范化 terms、相关画像版本与披露范围。条件变化使旧提案批准失效。两方服务收到同一摘要的两份用户批准后分别生成一致的结果卡；可能短暂处于一方已批准、另一方等待送达的状态。

结果卡显示双方、最终条件、已确认内容、仍待核实事项和下一步，支持 JSON 输出。先不交换真实联系方式。任何一方拒绝，显示明确原因并结束该双边会话，不影响其他候选。

## 验收

1. 四个真实子进程、四个端口、四份数据库；关闭其中一个，其他进程仍可操作。
2. 1 的请求到达 2、3、4，各自窗口都能看到本方接收事件；2 的硬条件失败不触发后续协商模型调用。
3. 1 与 3、4 有可记录的双向 HTTP 消息，双方本地状态持久化，窗口内容来自真实事件。
4. 1、3、4 均可出现本方问题卡；回答后保持原 PairSession，另一个候选继续运行。
5. 暂停后重启所属进程，问题仍在；重复投递不重复推进；离线对端恢复后可重试。
6. 模型输出接受严格校验；非法动作、越权字段、超时和坏 JSON 都有可见结果。无模型配置时不宣称真实模型通过。
7. 一方批准时无最终结果；两方批准同一提案才有结果卡；修改条件不能复用旧批准。
8. 修改候选事实可改变粗筛和最终结果，核心代码不写死候选 3 获胜。
9. 场地最小配置通过同一核心契约测试，不建设专属界面或完整议价流程。
10. TUI 输入期间仍可接收并展示对端事件；多会话回答与批准不能串线；窄终端可滚动，重启后能回答原问题。保留已有 10 项确定性测试作为旧原型回归依据。

前轮网页恢复竞态保留为旧原型已知问题，本阶段不扩展旧网页。新的 TUI 固定归属本进程身份，并校验所选会话与问题版本，避免继承旧网页身份切换模式。

## 实施边界与分工建议

A 负责通用模型、场景条件求值、双边会话、HTTP 收发、inbox/outbox、批准和多进程启动。B 负责 Policy 的确定性与模型适配、TUI、本方问题及回答输入、事件展示和结果卡。共享协议先冻结，再并行实现。TUI 与 headless 服务共用同一个运行时；模型适配、问题回答和传输均通过接口联调，不在 TUI 内重写业务状态机。

先用确定性 Policy 验收四进程收发及补问恢复，再在同一接口切真实模型。首次实现只保证固定可信对端、本机运行和合成资料。复杂发现、动态公网部署、第二套 UI、分布式共识和完善记忆管理留在后续。
